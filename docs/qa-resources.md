# QA resource limits

Mutation and fuzz checks use [the resource watchdog](../scripts/run-resource-bounded.py). Within the run's owned output root, it samples the larger of logical and allocated bytes for each file and directory, retains a capped combined log and records sampled disk usage, elapsed time, child exit status and refusal reason. Exceeding time, disk or log budgets fails the check. Results remain available for investigation.

Disk accounting is sampled, so writes can exceed the threshold between samples. A filesystem quota is required for a hard disk limit. Tool installation, Cargo's download cache and installed toolchains are separate prerequisites and remain outside the run's disk accounting and cleanup.

## Contributor tools and caches

The pinned [tool installer](../scripts/contributor-rust-tools.sh) separately guards each cold tool compilation: 4 GiB sampled temporary products, 900 seconds and a 4 MiB combined log. These are conservative bootstrap allowances, not measured minima or hard quotas. Smaller limits have not been established for every tool/host; exceeding a limit fails installation rather than accepting an unchecked tool. Compiler products use a fresh owned root, overriding inherited Cargo target/build directories for that command only. The watchdog emits a structured resource report, including observed peak disk and elapsed time, before success removes the temporary root; failure removes compiler products after confirmed child cleanup and reports the retained bounded log/resource evidence path. Unconfirmed cleanup retains the products rather than deleting paths a child might still write. CI uploads failed-install logs/reports for three days, outside the tool cache. An external hard kill can prevent cleanup.

Installed tool binaries and Cargo's registry/git downloads, rustup toolchains and existing project build caches are outside that transient compilation allowance. The installer does not delete owner caches or old toolchains. Their size depends on retained toolchains, targets and dependency versions; the compilation threshold is not an aggregate disk bound. Inspect owner state before explicitly choosing any cleanup; no automatic pruning is performed.

Cold and cached binaries both undergo an exact version query with a 10-second deadline, a 1 MiB log cap and a 4 MiB sampled probe-directory threshold. Version commands normally need only a short line; these are refusal allowances rather than required storage. Confirmed compiler products are removed before probing, so they do not occupy the probe allowance. Failed probes retain their nested logs and resource reports while preserving the installed binary. Every attempted phase must confirm process exit and cleanup before its temporary root can be removed; uncertain phases retain it and fail. Capability checks precede temporary-root creation.

CI caches contain only a single pinned tool's install root, never project build products or acceptance evidence. Cache keys retain OS, architecture, runner image, compiler inputs, the selected inventory row and installer logic. An unrelated tool inventory edit does not rebuild other tools. Only trusted `main` pushes save tool caches; PRs, release tags and manual runs restore exact keys without saving or broad fallback keys. Executable version mismatch fails. Old cache generations remain subject to the repository's configured GitHub cache retention/eviction policy; the installer does not delete pre-existing entries. See [GitHub's cache policy](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching).

On POSIX the watchdog retains an exited child with `waitid(..., WNOWAIT)` until after the final process-group signal, so its numeric PID/group cannot be reused for unrelated processes during cleanup. This requires Python 3.13+ on macOS and a Python 3.11+ with these APIs on Linux; nondefault `SIGCHLD` handlers are refused before launch. Lost child ownership refuses further numeric PID/group signals or waits and leaves cleanup explicitly unconfirmed. On Windows it uses `taskkill /T /F` for the active process tree; cleanup of descendants orphaned by an already exited Windows parent is not guaranteed.

POSIX cancellation first gives the live command one second to handle SIGINT, then forcibly stops its outer process group. This lets cargo-mutants stop the separate process groups it owns for builds and tests. Capped output is still drained during shutdown so cleanup diagnostics cannot block that handler. Group cleanup, leader reaping and output draining have finite waits; cleanup errors remain separate from the original refusal, and unconfirmed products are retained for inspection. Exceeding the cooperative grace is itself an unconfirmed-cleanup refusal: forcibly killing the outer group does not establish that separately grouped descendants stopped. A non-cooperating process that escapes its group still requires OS containment; this watchdog is not a process sandbox.

## Mutation review

Install `cargo-mutants` at the version in [the tool inventory](../scripts/contributor-rust-tools.sh), fetch locked dependencies, and run:

```sh
cargo fetch --locked
python3 scripts/mutation-audit.py --output /path/outside/checkout/mutation-results
```

The output directory must not exist, its parent must exist, and both must be outside the actual Cargo workspace, including when `--dir` names a member crate. Unset shared Cargo target/build directory overrides before running. Builds use locked dependencies offline. The runner requires enough free space for the campaign disk budget or the separate 4 MiB pin-probe allowance, whichever is larger, before starting. Before the campaign, the installed `cargo-mutants` version is checked through the same owned watchdog: ten seconds, a 4 MiB sampled directory and a 1 MiB retained log. The version phase has its own log, status and cleanup record under `tool-version/`; a wrong pin, probe refusal or unconfirmed cleanup leaves an incomplete source-bound audit and never starts mutation execution. Interrupted probes use the same cooperative wrapper teardown as campaigns. A diff selection is checked before creating output and copied into owned evidence, so its input survives independently of the original path.

The runner's `--help` describes resource and selection options. Defaults are up to two workers, a 4 GiB sampled disk budget and a 30-minute campaign deadline, plus the separate pin probe and finite cleanup waits. `--jobs` can explicitly select up to the available CPU count; the shared jobserver limits compiler concurrency. More workers duplicate compiled workspaces and run more test processes concurrently, so select disk, memory and time allowances from measured runs. This is not a promise of a universal speedup. Each worker reuses its own build products; incremental compilation and debug information are disabled. Existing targets and VCS data are not copied. Explicit relative Cargo build paths keep products in owned worker roots.

The 4 GiB default is a conservative refusal threshold for two worker builds plus source copies and evidence, not a required minimum or proven maximum. The dominant cost is one compiled workspace per worker; the full disk budget also covers scenario logs and diffs, while the separate 8 MiB cap covers combined console output. Resource reports provide sampled measurements for choosing a smaller allowance or one worker. Changing dependencies, compiler, host or worker count can change the requirement. A hard maximum needs a filesystem quota; the watchdog can overshoot between samples. Toolchain and owner download caches remain outside this budget and are never cleaned by this runner.

Survivor logs, diffs, resource reports and structured outcomes remain in the output directory. Choose a fresh output directory for each invocation. Confirmed worker roots are removed after success or failure. If process cleanup or the reader cannot be confirmed, the runner retains its owned scratch and names it in `audit.json`; do not delete it while recorded processes may still be writing. Interrupted and resource-refused runs remain incomplete. Explicitly select a larger overall budget for a separately authorized full release campaign when needed; do not hide a timeout or change an expectation to force completion.

Use `--file`, `--exclude-file`, `--regex` or `--in-diff` for focused iteration; even an exclusion-only selection is focused and its exact exclusions are retained. Every run retains the unmutated baseline, complete workspace test selection and locked dependencies. Mutation tests default to one Rust test thread per worker to avoid multiplying each worker's test concurrency; an explicit `RUST_TEST_THREADS` setting is retained. The complete workspace test selection remains unchanged. The pinned stable test harness refuses `--fail-fast` as an unstable option, so this optimization is unavailable; no nightly or bootstrap override is enabled. Ordinary maintainer, minimum-Rust and native acceptance test settings are unchanged. A focused selection does not replace the full release review. The runner verifies exact unique planned mutant identities against outcomes, baseline/build/test evidence, summary counts and the tool's exit status, including nonzero survivor and timeout results. Those nonzero statuses remain nonzero. `execution_complete` describes complete, stable-source execution; it does not mean every mutant was caught or reviewed. Inspect every survivor and timeout before declaring that review complete; `full_review_complete` is never inferred from a process exit.

`audit.json` binds the host and actual source bytes before and after execution, including tracked and nonignored Git files and executable/symlink identity. Source changes invalidate the run. Freeze the reviewed release commit and keep inputs stable throughout the full campaign. Source hashes establish identity, not review quality, and a campaign on one host does not establish mutation coverage of code conditional on other operating systems.
